# 会议录音转写与会议纪要生成工具 - 技术方案

## 1. 选型前提

本方案基于当前 PRD：

- 第一版是本地网页工具，用户在本机浏览器打开页面使用。
- 单人使用，不做账号登录。
- 数据默认保存在本机，不做云端账号系统。
- 客户在中国大陆。
- 录音主要是中文普通话。
- 单个录音通常 30 分钟以上。
- 需要用“发言人1、发言人2”区分不同说话人。
- 用户可以修改转写文字、会议纪要和报告提纲。
- 需要历史记录长期保存在本机。
- MVP 1A 先跑通真实核心流程，MVP 1B 再做 Word/PDF 导出。

当前默认正式方案统一改为阿里云百炼体系：

- 前端和后端：Next.js。
- 语音转文字：阿里云百炼 Fun-ASR 录音文件识别。
- 默认语音转写模型：`fun-asr`。
- 原 `qwen3-asr-flash-filetrans` 适合长音频识别，但不支持说话人分离，不再作为默认语音转写方案。
- Fun-ASR 支持 `diarization_enabled`，开启后结果中可返回 `speaker_id`，系统可以映射为“发言人1、发言人2”。
- 会议纪要和报告提纲生成：阿里云百炼 Qwen 文本生成模型，默认使用 Qwen。
- 历史记录：SQLite。
- Word/PDF 导出：放在 MVP 1B，不进入 MVP 1A。

## 2. 开源复用原则

在正式从零开发前，优先查找是否有 GitHub 开源项目可以参考或复用。

重点参考这些方向：

- 会议录音转写项目。
- 会议纪要生成项目。
- 说话人区分项目。
- 本地历史记录保存项目。
- Word/PDF 导出项目。

但不能盲目照搬开源项目。每个候选项目都需要评估：

- 许可证是否允许使用。
- 项目是否还在维护。
- 技术栈是否和当前方案接近。
- 代码复杂度是否适合第一版。
- 是否容易改成单人本机网页工具。
- 是否真的支持中文普通话、长录音、发言人区分等核心需求。
- 适配成本是否比自己开发更低。

如果开源项目只是某一小部分做得好，可以只参考或复用这一小部分；如果整体太复杂、太旧、许可证不合适，就只作为学习参考，不直接使用。

## 3. UI 风格原则

第一版 UI 不追求复杂设计稿，但要做到现代、干净、专业。

整体风格参考 Notion、Linear、Apple Notes 这类工具型产品：

- 页面清爽，信息层级明确。
- 使用卡片式布局。
- 左侧放历史记录栏。
- 右侧放主要工作区。
- 上传、复制、导出等按钮要清楚好找。
- 转写文字、会议纪要、报告提纲要分区展示。
- 加载中要有明确提示，让用户知道系统正在处理。
- 没有上传录音或没有历史记录时，要有清楚的空状态提示。
- 不做花哨动画，不做复杂装饰。

第一版 UI 的目标是让用户一眼知道“现在该点哪里、结果在哪里、下一步能做什么”。

## 4. Provider 可切换原则

虽然当前默认正式方案是阿里云百炼，但代码设计上不要把供应商写死在页面组件里。

后续开发时要遵守：

- 不要把语音转写供应商写死在页面组件里。
- 不要把大模型供应商写死在页面组件里。
- 后续代码应封装 Speech Provider，用来管理语音转写供应商。
- 后续代码应封装 LLM Provider，用来管理大模型供应商。
- 当前默认 Speech Provider 是 `aliyun`。
- 当前默认 LLM Provider 是 `qwen`。

这样做的好处是：第一版先用阿里云百炼快速交付，如果以后客户环境变化，也可以更容易切换到其他供应商。

## 5. 方案 A：阿里云百炼正式方案

一句话说明：用一个本地网页项目把页面和后台处理放在一起，真实转写和大模型生成都走阿里云百炼。

这是当前最推荐的方案。

### 前端用什么

使用 Next.js。

可以把它理解成“做网页的工具”。用户看到的上传区域、转写文本、会议纪要、报告提纲、历史记录，都用它来做。

### 后端用什么

使用 Next.js 自带的后端能力。

可以把它理解成“网页背后帮忙干活的部分”。它负责接收音频、调用阿里云百炼、保存历史记录、生成导出文件。

### 语音转文字用什么 API

使用阿里云百炼 Fun-ASR 录音文件识别。

默认使用模型：`fun-asr`。

选择它作为默认正式方案的原因：

- 客户在中国大陆。
- 主要是中文普通话。
- 录音通常 30 分钟以上。
- 适合会议记录、访谈整理等长音频场景。
- 明确需要“发言人1、发言人2”区分，Fun-ASR 支持 `diarization_enabled` 说话人分离。
- 原 `qwen3-asr-flash-filetrans` 虽然适合长音频识别，但不支持说话人分离，因此不作为当前默认方案。
- 国内账号、付款、访问、发票和交付更方便。

### 是否支持发言人1/2区分

支持。

Fun-ASR 开启 `diarization_enabled` 后，结果中可返回 `speaker_id`。系统把 `speaker_id` 映射为“发言人1、发言人2、发言人3”这种编号，不自动识别真实姓名。

### 会议纪要生成用什么大模型 API

使用阿里云百炼 Qwen 文本生成模型。

默认使用 Qwen，例如 `qwen-plus`。

选择它作为默认正式方案的原因：

- 和语音转写同属阿里云百炼体系。
- 客户只需要管理一个平台。
- 账号、账单、付款、发票和后续维护更方便。
- 国内交付比海外 API 更顺。

### 历史记录保存在什么地方

保存在本机 SQLite 数据库里。

可以把 SQLite 理解成一个本地小数据库文件。它不需要单独买服务器，也不需要云账号，适合单人本机使用。

音频文件和导出的文件可以保存在本机项目目录下的指定文件夹里。

长录音上传说明：

- 默认使用阿里云百炼提供的临时上传方式，避免把客户文件上传到开发方自己的 OSS。
- OSS 只作为未来可选能力：只有客户提供自己的 OSS，并明确开启后，才上传到客户 OSS。
- 当前交付版本不默认读取或使用开发方 OSS 配置。

长音频处理说明：

- 30 分钟以上音频按异步任务处理，页面需要显示任务状态，而不是让用户误以为卡住。
- 1-2 小时音频可以处理，但需要更长等待。
- 标准会议模式开启说话人分离，适合多人会议，但会更慢。
- 快速转写模式关闭说话人分离，通常更快，适合先拿到文字。
- 开启说话人分离时，建议单个音频不超过 2 小时。
- 超过 2 小时且需要发言人分离，建议拆分处理。
- 超过 2 小时但不需要发言人分离，可以使用快速转写模式。
- 页面显示的预计处理时间只是估算，不是承诺。

### Word/PDF 导出怎么做

Word：由后端根据最终内容生成 `.docx` 文件。

PDF：第一版可以用通用排版生成 PDF，或者先用浏览器打印成 PDF 的方式实现。

不做公司固定模板，只保证内容清楚、能正常导出。

注意：Word/PDF 导出放在 MVP 1B，不进入 MVP 1A。MVP 1A 先完成上传、转写、编辑、生成纪要/提纲、保存历史记录和复制。

### 优点

- 更适合中国大陆客户。
- 更适合中文普通话和长音频会议场景。
- 语音转写和文本生成都在阿里云百炼体系内，管理更简单。
- 付款、发票、访问和交付更方便。
- Next.js + SQLite 的结构仍然适合小白逐步推进。

### 缺点

- 需要配置阿里云百炼账号和 API Key。
- 长音频识别可能涉及文件上传、任务等待和结果查询，需要认真处理状态提示。
- 如果后续切换供应商，需要依赖 Provider 封装，不要把供应商逻辑散落在页面里。

### 适合什么情况

- 客户在中国大陆。
- 主要处理中文普通话会议录音。
- 录音经常 30 分钟以上。
- 希望真实交付时账号、付款、发票和维护更方便。
- 第一版仍然是单人本机工具。

### 不适合什么情况

- 客户明确要求使用海外 API。
- 客户已有固定的 OpenAI 或 AssemblyAI 采购体系。
- 客户要求完全离线部署。

## 6. 方案 B：海外 API 备选方案

一句话说明：保留 AssemblyAI 和 OpenAI 作为海外备选，不作为中国大陆客户的默认正式方案。

### 前端用什么

仍然使用 Next.js。

### 后端用什么

仍然使用 Next.js 自带后端能力。

### 语音转文字用什么 API

AssemblyAI 可以作为海外备选。

它支持语音转文字和说话人区分，但对于中国大陆客户，不作为默认方案。主要原因是账号、付款、访问稳定性、发票和交付便利性不如国内平台顺手。

### 是否支持发言人1/2区分

支持。

AssemblyAI 可以返回说话人标签，系统可以整理成“发言人1、发言人2”。

### 会议纪要生成用什么大模型 API

OpenAI 可以作为海外备选。

它适合生成会议纪要和报告提纲，但对于中国大陆客户，不作为默认方案。

### 历史记录保存在什么地方

仍然保存在本机 SQLite。

### Word/PDF 导出怎么做

仍然放在 MVP 1B，使用通用 Word/PDF 导出方式。

### 优点

- 海外 API 能力成熟。
- 如果客户本来就有海外 API 账号，接入路径较清楚。

### 缺点

- 不适合作为中国大陆客户默认交付方案。
- 账号、付款、访问、发票和后续维护可能更麻烦。
- 供应商分散，语音转写和大模型生成不在同一平台。

### 适合什么情况

- 客户明确可以使用海外 API。
- 客户已有海外 API 账号和付款方式。

### 不适合什么情况

- 当前这个中国大陆客户的默认交付。
- 客户希望一个平台统一管理。

## 7. 方案 C：低成本备选方案

一句话说明：DeepSeek 可以作为低成本文本生成备选，但不作为当前默认正式方案。

### 前端用什么

仍然使用 Next.js。

### 后端用什么

仍然使用 Next.js 自带后端能力。

### 语音转文字用什么 API

语音转写仍建议优先使用阿里云百炼 Fun-ASR。

DeepSeek 主要是文本大模型，不负责本项目的长音频转写主流程。

### 是否支持发言人1/2区分

发言人区分仍依赖语音转写服务返回的说话人信息。

### 会议纪要生成用什么大模型 API

DeepSeek 可以作为低成本文本生成备选。

它可以根据转写文字生成会议纪要和报告提纲，但当前默认方案仍然是阿里云百炼 Qwen。

### 历史记录保存在什么地方

仍然保存在本机 SQLite。

### Word/PDF 导出怎么做

仍然放在 MVP 1B，使用通用 Word/PDF 导出方式。

### 优点

- 文本生成成本可能更低。
- 可以作为后续降本选项。

### 缺点

- 不负责长音频转写。
- 会让默认方案变成多个平台混用，增加客户管理成本。
- 当前客户更需要国内统一平台交付，所以不作为默认方案。

### 适合什么情况

- 后续客户特别关注文本生成成本。
- 已经跑通阿里云转写后，只想替换会议纪要生成模型。

### 不适合什么情况

- 当前第一版默认交付。
- 希望一个平台统一管理账号、付款和维护。

## 8. 推荐方案

推荐当前项目采用：方案 A，阿里云百炼正式方案。

原因：

- 客户在中国大陆，国内平台更方便交付和维护。
- 会议录音主要是中文普通话。
- 单个录音通常 30 分钟以上，更适合选择长音频录音文件识别方向。
- Fun-ASR 适合会议记录、访谈整理等长音频场景，并支持说话人分离。
- `qwen3-asr-flash-filetrans` 适合长音频识别，但不支持说话人分离，不能满足客户明确要求的“发言人1/发言人2”区分。
- Qwen 文本生成和 Fun-ASR 同属阿里云百炼体系，客户只需要管理一个平台和一套账单。
- SQLite 适合本机长期保存历史记录，不需要额外部署数据库。
- Next.js 仍然适合第一版本地网页工具。
- Word/PDF 导出明确放在 MVP 1B，不进入 MVP 1A。

建议执行顺序：

1. MVP 0：保留已完成的页面流程。
2. MVP 1A：把真实转写和文本生成切换到阿里云百炼体系。
3. MVP 1B：再补 Word/PDF 导出。

## 9. 当前默认与备选关系

- 默认语音转写：阿里云百炼 Fun-ASR，模型 `fun-asr`。
- 默认开启说话人分离：`diarization_enabled=true`。
- 可选说话人数量参考：`speaker_count` 默认留空，让 Fun-ASR 自动判断实际说话人数。
- 不建议第一版固定 `speaker_count`，因为客户会议里可能有 2 人、3 人或更多人。只有在明确知道人数时，才可以临时设置该值作为算法参考。
- 默认文本生成：阿里云百炼 Qwen，默认模型 `qwen-plus`。
- AssemblyAI：海外备选，不作为国内客户默认方案。
- OpenAI：海外备选，不作为国内客户默认方案。
- DeepSeek：低成本备选，不作为当前默认方案。

环境变量中 `ALIYUN_API_KEY` 和 `QWEN_API_KEY` 实际上可以使用同一个阿里云百炼 API Key。

为了代码职责清晰，环境变量里可以先分开命名。后续接入时如果发现统一成 `DASHSCOPE_API_KEY` 更合适，也可以再调整。
